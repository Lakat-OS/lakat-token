# Lakat token

`LKT`, an upgradeable ERC-20 with a Merkle-proof distributor that holds the
entire initial supply.

| contract | | |
|---|---|---|
| [`src/Lakat.sol`](src/Lakat.sol) | `Lakat` | ERC-20 + `ERC20Permit`, UUPS upgradeable. Fixed supply of 1,000,000,000 LKT (18 decimals), minted once at initialisation. |
| [`src/LakatTokenDistributor.sol`](src/LakatTokenDistributor.sol) | `LakatTokenDistributor` | UUPS upgradeable. Receives that entire supply and releases it against Merkle proofs. |

Both are deployed behind ERC-1967 UUPS proxies. **The owner of both — and
therefore the only address that can upgrade either implementation, publish a
Merkle root, or sweep unclaimed tokens — is:**

```
0x9D9c216aD173bB2B265f58E10f281Bf6070e61a0
```

Both contract addresses are the **ERC-1967 proxies** — the permanent addresses
to hold, integrate against, and add to a wallet. The implementations behind
them change on upgrade and should not be used directly.

To check a deployment matches this table:


## Requirements

- [Foundry](https://book.getfoundry.sh/getting-started/installation)
- Node.js 18+ (for the Merkle tooling)

```
git submodule update --init --recursive
npm install
forge test --force
```

`setup.sh` is the OpenZeppelin Wizard bootstrap and is only needed to
initialise a fresh project; this repo is already initialised.

`--force` matters: `openzeppelin-foundry-upgrades` validates upgrade safety
against build artifacts, and a stale `out/` makes it complain.

## How the distribution works

The owner publishes a Merkle root. Anyone can then submit a claim, and the
tokens always go to the account encoded in the leaf — so a relayer can pay the
gas on a recipient's behalf.

Leaves are encoded exactly as OpenZeppelin's
[`@openzeppelin/merkle-tree`](https://github.com/OpenZeppelin/merkle-tree)
`StandardMerkleTree` encodes them — double-hashed ABI encoding of
`["uint256", "address", "uint256"]` = `(index, account, amount)`:

```
keccak256(bytes.concat(keccak256(abi.encode(index, account, amount))))
```

`test/MerkleTreeCompat.t.sol` pins that compatibility by claiming on-chain
against a root and proofs generated by the JS tooling in `merkle/`.

## 1. Build the tree

The default input is `merkle/allocations.json` — a JSON array of
`{ address, tokens }` (human-readable decimal) or `{ address, amount }` (base
units) objects:

```json
[
  { "address": "0x70997970C51812dc3A010C7d01b50e0d17dc79C8", "tokens": "1000000" },
  { "address": "0x3C44CdDdB6a900fa2b585dd299e03d12FA4293BC", "amount": "1000000000000000000" }
]
```

```
cp merkle/allocations.example.json merkle/allocations.json
# edit merkle/allocations.json
npm run merkle:build
npm run merkle:root            # just the root, for $(…)
```

**CSV works too**, for a list that came out of a spreadsheet. Pass the path
explicitly — the format is chosen by file extension, `.json` is JSON and
anything else is parsed as CSV:

```
node merkle/build-tree.mjs merkle/allocations.csv
```

```csv
address,tokens
0x70997970C51812dc3A010C7d01b50e0d17dc79C8,1000000
0x3C44CdDdB6a900fa2b585dd299e03d12FA4293BC,250000.5
```

The header is optional — with no header the first two columns are taken as
address and amount. `,` and `;` delimiters, CRLF, quoted fields, a UTF-8 BOM,
blank lines and `#` comments are all handled. Both formats produce an identical
root for the same list; `merkle/allocations.example.csv` is the same data as
`merkle/allocations.example.json` and yields the same root.

Amounts are human-readable tokens by default, converted with `--decimals`
(18). Use an `amount` key, a CSV column named `amount`, or `--units base` if
your figures are already in base units. `tokens` and `amount` differ by a
factor of 10^18 — check the `total:` line the script prints before publishing
anything.

**Duplicate addresses are an error by default.** Because leaf indices are array
positions, a repeated address gets two independently claimable leaves and is
paid twice — almost always a bad merge of two lists rather than an intent. Pass
`--on-duplicate sum` to merge the rows, or `--on-duplicate keep` if you really
do want two claims.

Leaf indices being positional also means **you must never reorder or insert
into a list whose root is already published** — append only, or publish a fresh
root for the remaining allocations.

The build writes two files into `--out` (default `merkle/out`):

- `tree.json` — the dumped Merkle tree. **Keep it**; `proof.mjs` reads this,
  not the allocations file, so that proofs always come from the exact tree
  whose root you published.
- `claims.json` — the root, the totals, and an address → array of
  `{index, amount, proof}` map you can serve to a frontend. It is an array per
  address because `--on-duplicate keep` allows several leaves for one address;
  with the default policy every array has exactly one entry.

## 2. Deploy

One script, [`script/Deploy.s.sol`](script/Deploy.s.sol), deploys everything.

### Mainnet

```
forge script script/Deploy.s.sol:Deploy \
  --rpc-url $RPC_MAIN \
  --broadcast --slow \
  --verify --etherscan-api-key $ETHERSCAN_API_KEY \
  --private-key $PRIVATE_KEY \
  -vvv
```

Every line except the last needs a trailing `\`, including the one before
`-vvv` — otherwise the shell runs `-vvv` as its own command.

With the script's own inputs in the environment:

| variable | | |
|---|---|---|
| `OWNER` | required | final owner and UUPS upgrader of **both** proxies — `0x9D9c216aD173bB2B265f58E10f281Bf6070e61a0` |
| `MERKLE_ROOT` | optional | first distribution root, from `npm run merkle:root`. Omit to publish it later (step 3). |
| `RPC_MAIN` | | mainnet RPC endpoint |
| `ETHERSCAN_API_KEY` | | for `--verify` |
| `PRIVATE_KEY` | | the **deployer** key, not the owner. It needs gas, briefly owns the distributor during setup, and holds nothing afterwards. |

```
export OWNER=0x9D9c216aD173bB2B265f58E10f281Bf6070e61a0
export MERKLE_ROOT=$(npm run --silent merkle:root)     # optional
```

`--slow` sends one transaction at a time and waits for each receipt. Keep it:
every step after the first depends on an address produced by the previous one.

Drop `--broadcast` to simulate first. That is worth doing — the simulation runs
the same assertions as the real thing.

### Alternative: signing with Google Cloud KMS

Swap `--private-key $PRIVATE_KEY` for `--gcp --sender $GCP_DEPLOYER`, so no key
material touches the machine running the script. The key is located through the
`GCP_*` environment variables Foundry reads (project, location, key ring, key
name, key version); check `forge script --help` for the exact set your version
expects. `--sender` must be the address that key controls, because the script
uses it as the temporary owner before handing over.

### Troubleshooting

**`Error: failed to determine network family from endpoint`**, with a body like
`Unsupported method: anvil_nodeInfo`. This is a regression in Foundry **1.8.0**:
`forge script` probes the endpoint with `anvil_nodeInfo` and treats any
unsuccessful response as fatal, so it only works against Anvil. `cast` and
`forge create` are unaffected. No flag disables the probe — `--network
ethereum`, `--chain 1` and `--skip-simulation` all still fail. Use an older
Foundry:

```
foundryup --use v1.7.1     # verified working; 1.5.1-stable also works
```

### What the script does

1. deploys the distributor implementation + UUPS proxy, owned by the deployer;
2. deploys the Lakat implementation + UUPS proxy, minting the **entire initial
   supply directly to the distributor proxy**;
3. binds the token on the distributor (`setToken`, one-shot);
4. publishes `MERKLE_ROOT` if one was given;
5. transfers distributor ownership to `OWNER`.

It then asserts the supply landed in the distributor, the token is bound, and
both proxies are owned by `OWNER` — so a half-configured deployment reverts
instead of being left behind.

The distributor is deployed **before** Lakat so that Lakat can mint straight
into it. The supply is therefore never held by the deploying key — there is no
window in which a compromised deployer controls the tokens, and no follow-up
transfer to forget. That ordering is also why the distributor's `initialize`
takes only an owner: the token address does not exist yet, so it is bound a
moment later with `setToken`, which can only ever be called once.

Ownership starts with the deployer rather than `OWNER` for two reasons: the
setup calls above are `onlyOwner` and must be scriptable, and initialising the
proxy atomically closes the window in which anyone could call `initialize` on a
fresh UUPS proxy and seize it. `OWNER` can therefore be a multisig or a cold
key that never sends a setup transaction.

`transferOwnership` is single-step (OZ `Ownable`, not `Ownable2Step`) — check
`OWNER` carefully, a wrong address is not recoverable and takes the upgrade
rights with it.

## 3. Publish a root

Only needed if you skipped `MERKLE_ROOT` at deploy time, or when starting a new
round. **Must be sent by the owner**, `0x9D9c216aD173bB2B265f58E10f281Bf6070e61a0`:

```
DISTRIBUTOR=0xe36523eA4190D650CE5E2bE7be24b131c515d795 MERKLE_ROOT=0x… \
  forge script script/Deploy.s.sol:SetMerkleRoot \
    --rpc-url $RPC_MAIN --broadcast --slow \
    --gcp --sender $GCP_DEPLOYER -vvv
```

Each `setMerkleRoot` bumps `distributionId` and starts a fresh round: claim
bookkeeping from the previous root no longer blocks anything, so a replacement
root must contain only the allocations that should still be claimable.

## 4. Claim

```
npm run merkle:proof -- 0xRecipient --distributor 0xe36523eA4190D650CE5E2bE7be24b131c515d795
node merkle/proof.mjs --all --json > proofs.json   # every leaf at once
```

This reads `merkle/out/tree.json` (override with `--tree`), so run
`merkle:build` first. It prints the proof and a ready-to-run `cast send` for

```solidity
claim(uint256 index, address account, uint256 amount, bytes32[] proof)
```

Anyone may send that transaction; the tokens go to `account` either way.

## Owner-only functions

All of these require `0x9D9c216aD173bB2B265f58E10f281Bf6070e61a0`:

| contract | function | |
|---|---|---|
| `LakatTokenDistributor` | `setToken(address)` | bind the distributed token; callable once, done at deploy |
| | `setMerkleRoot(bytes32)` | publish a root, starting a new distribution round |
| | `sweep(address,uint256)` | recover unclaimed LKT |
| | `sweepToken(address,address,uint256)` | recover any other ERC-20 sent here by mistake |
| | `upgradeToAndCall(address,bytes)` | UUPS upgrade |
| | `transferOwnership(address)` | single-step, no undo |
| | `renounceOwnership()` | ⚠️ inherited from `Ownable`; see below |
| `Lakat` | `upgradeToAndCall(address,bytes)` | UUPS upgrade |
| | `transferOwnership(address)` | single-step, no undo |
| | `renounceOwnership()` | ⚠️ inherited from `Ownable`; see below |

⚠️ `renounceOwnership()` sets the owner to the zero address. On the distributor
that would permanently strand every unclaimed token — no further root could be
published and `sweep` would be unreachable — and on either contract it makes
the implementation unupgradeable forever. Nothing in this repo calls it; it
comes with OZ `Ownable`. Override it to revert if you want that door shut.

`Lakat` has no mint function beyond the one-time mint in `initialize`, so the
supply is fixed at 1,000,000,000 LKT unless the implementation is upgraded.
